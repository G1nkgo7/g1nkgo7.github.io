Agent 不是简单的”套壳 LLM + 给工具”。它是”推理 → 选工具 → 执行 → 观察反馈 → 再推理”的闭环系统。这篇从核心概念出发，串讲工具管理的工程解法，再到 8 种主流设计模式的演进逻辑。

一、什么是 Agent

核心定义

Agent 是基于大模型、具备决策能力的系统，能够通过调用工具完成多步任务：

本质：一个”决策 + 执行”的闭环系统，而不是单次生成。

二、工具管理：工具多了怎么办

问题

Function Call 提供的工具数量越多，模型选择工具的准确率反而下降——选择空间大了，误选的概率自然上升。

解法一：工具路由（Tool Routing）

先做意图分类，只暴露相关的工具给模型，缩小决策空间：

  • 用户要做计算 → 只保留计算相关工具
  • 用户想出行 → 只保留天气、交通相关工具

具体实现：

  • Tool Filtering：根据工具描述文本做 embedding，检索到 Top-K 最相关的工具
  • Planner-Executor：先规划需要哪些步骤，再执行；本质上是降低 tool selection 的 entropy（熵）——选择空间减小，不确定性降低

解法二：Tool Prompt 优化

  • 工具描述要清晰、避免歧义
  • 工具之间功能尽量不要重叠（否则模型容易混淆）
  • 不过在实际系统中（如 Claude Code 的 skill），描述通常比较简短，需要在简洁和信息量之间平衡

三、协议与框架

MCP（Model Context Protocol）

是什么：统一大模型与外部工具、数据交互的开放协议。

作用：

  • 标准化工具调用
  • 统一上下文传递
  • 支持多 Agent 协作

可以类比为”适配器架构”：每个模型只对接 MCP，MCP 统一向外对接各种工具，实现模型与工具的解耦，提升系统可扩展性。

Skill

是什么：对一类任务能力的封装，通常由 prompt + 工具 + 执行流程 组成。

Skill 是可复用的任务模块，是 Agent 能力抽象层。

Agent 框架

常见的 Agent 框架有：

  • LangChain / LangGraph：提供 Tool Calling、Memory、Workflow（DAG）、Multi-Agent 的能力

框架的作用是把工具调用、记忆管理、流程控制等基础设施封装好，让开发者专注业务逻辑。

四、Multi-Agent 协作

难点

问题 描述
通信成本 消息多 → 延迟高
信息不一致 不同 Agent 上下文不同 → 结论冲突
决策冲突 多个 Agent 给出不同方案
任务拆分 如何合理分工
循环/死锁 互相调用 → 无限循环

常见解法

  • 中央调度（Planner）：由一个中央规划器统一派发任务
  • 角色分工（Role-based）：每个 Agent 有明确职责，避免功能重叠
  • 共享 Memory：所有 Agent 读写同一份上下文，保证信息一致性
  • 限制调用深度：设置最大调用链深度或轮次，防止死循环

五、Agent 设计模式

以下按时间线和复杂性递增排列，理解每种模式的核心改进动机比死记架构图更重要。

1. ReAct（2022.10）

核心思想：将 Reasoning（推理）和 Acting（行动）结合起来。

在 ReAct 之前，Reasoning 和 Acting 是割裂的。比如让孩子去厨房拿胡椒粉：

  • 先看台面上有没有
  • 再看灶台抽屉里
  • 最后看吊柜里

没有 ReAct：不管第几步找到了，ta 都会把所有地方翻一遍（按预设列表执行到底）。

有 ReAct：

模式：Thought → Action → Observation 循环，每步观察后再决策下一步。

2. Plan & Solve

核心改进：先制定完整计划，再逐步执行，且执行中可灵活调整计划。

类比：ReAct 适合”去厨房拿胡椒粉”（简单、顺序明确），Plan & Solve 适合”做西红柿炒鸡蛋”——需要计划步骤，且过程中可能变化（打开冰箱发现没西红柿了，就新增”买西红柿”这一步）。

特点：本质上是 Zero-shot CoT 的改进版，在回答前先让模型制定计划。

3. ReWOO（Reason Without Observation）

核心改进：去掉显式的 Observation 步骤，将其隐式嵌入到下一步的执行器中。

类比：常见审批流——目标是要拿到 C 文件：

  1. 去 A 部门拿 a 文件
  2. 拿 a 文件去 B 部门办 b 文件
  3. 拿 b 文件去 C 部门办 c 文件 → 完成

其中 B 和 C 部门对上游文件的”审查”本身就是 Observation，只是不需要显式写出来——由下一步执行器自动获取上一步的输出。

模式：Plan1 → Action1 → Plan2(依赖Plan1输出) → Action2 → ...

4. LLMCompiler

核心改进：并行执行相互独立的任务，提升效率。

问题：”张译和吴京差几岁”——搜索张译年龄和搜索吴京年龄是独立的，可以并行。

做法：Planner 生成一个 DAG（有向无环图），把互相依赖的节点串行，独立节点并行，最后合并结果。

模式 串行/并行 场景
ReAct 串行 简单顺序任务
Plan & Solve 串行 需要计划的任务
LLMCompiler 并行 多变量独立查询

5. Basic Reflection

核心思想：引入”检查”机制，像学生写作业、老师批改。

  • Generator：生成初始答案
  • Reflector：检查答案，给出改进建议
  • 循环迭代直到满足条件

模式：Generate → Reflect → Revise → Reflect → ...

6. Reflexion

核心改进：在 Basic Reflection 基础上引入外部评估和强化学习的思路。

  • 用外部数据（而非模型自己）来评估回答的准确性
  • 强制模型反思回答中 缺失（Missing） 和 多余（Superfluous） 的部分
  • 改进意见更具建设性

流程：思考(含反思) → 回答 → 评估 → 修改 → 循环

7. LATS（Language Agent Tree Search）

核心改进：融合树搜索 + ReAct + Plan & Solve + Reflection + 强化学习。

一句话：对各种模式的集大成者。

  • 用树搜索探索多条推理路径
  • 对每条路径做 Reward 评估（强化学习思路）
  • 融入 Reflection 持续改进
  • 最终拿到最佳路径

架构：多轮 Basic Reflection，多个 Generator 和 Reflector 同时工作。

提示词模板与之前的 Reflection、Plan & Solve、ReAct 差别不大，核心区别在于多了树搜索的评估和回溯机制。

8. Self-Discover

核心改进：让模型在更细粒度上对任务本身进行反思。

Plan & Solve 反思的是”计划是否需要补充”，而 Self-Discover 反思的是任务本身的拆解方式。

结构：

  1. Selector：从一批反思策略中选择合适的
  2. Adaptor：用选中的策略进行反思
  3. Implementor：根据反思结果重新推理

六、设计模式演进一览

模式 核心改进 出现时间
ReAct Reasoning + Acting 结合，Observation 驱动 2022.10
Plan & Solve 提前规划，可动态调整 —
ReWOO Observation 隐式化 —
LLMCompiler 并行执行独立任务（DAG 调度） —
Basic Reflection 生成 → 检查 → 修改 循环 —
Reflexion 引入外部评估 + 强化学习 —
LATS 树搜索 + 多模式融合 —
Self-Discover 对任务本身进行元反思 —

小结：面试怎么聊 Agent

  1. 定义要准确：Agent = 推理 + 工具 + 观察反馈的闭环，不是单次 response
  2. 工具管理有思路：路由 → 筛选 → 优化描述 → Planner-Executor，核心是降低 entropy
  3. 协议和框架要区分：MCP 是通信协议，Skill 是能力封装，LangChain/LangGraph 是基础设施
  4. Multi-Agent 要聊痛点：不要只说”可以分工协作”，要说通信成本、信息不一致、循环死锁
  5. 设计模式要懂演进逻辑：每一种新模式的动机比架构细节更重要——为什么之前的模式不够，新模式解决了什么
